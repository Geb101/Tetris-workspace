# Общий процесс подготовки документации

## Схема процесса

```text
Требования и цели
        ↓
Структура документации
        ↓
Написание текста главы
        ↓
Проверка критиком (ИИ-агент)
        ↓
Проверка на реальном читателе
        ↓
Правки по результатам проверок
        ↓
Перевод на английский язык
        ↓
Верстка в Google Docs (Antigravity + Google Docs MCP)
        ↓
Визуальная валидация (BrowserSkill)
        ↓
Тест на неопытном читателе
        ↓
Финальные правки
        ↓
Передача через Google Docs + ссылка на репозиторий
```

## Этапы процесса

### 1. Планирование

- Зафиксировать требования к главе.
- Определить, что читатель должен уметь после прочтения.
- Решить, какие понятия объясняются в этой главе, а какие уже известны.

### 2. Написание

- Писать короткими абзацами: одно понятие — один абзац.
- Вводить термины по одному, не объединять несколько новых понятий.
- Описывать действия через результат, а не через намерение.
- Не использовать директивные формулировки без необходимости.
- Не включать исторические справки, если они не помогают выполнить действие.

### 3. Проверка критиком

- Критик оценивает текст с позиции читателя без игрового опыта.
- Проверяются: однозначность, порядок шагов, противоречия, пропуски.
- Замечания делятся на критичные и редакторские.
- Редакторские замечания можно отложить, критичные исправляются до передачи.

### 4. Проверка на реальном читателе

- Текст читает человек, знакомый с темой, но оценивающий как редактор.
- Фиксируются: неудачные формулировки, структура, уместность содержания.
- Оценка сохраняется в `03-проверка/`.

### 5. Перевод

- Перевод выполняется после завершения русской версии.
- Переведённый текст проходит отдельную проверку на естественность.
- Проверяется уместность содержания для технической документации, а не только точность перевода.

### 6. Верстка

- Выполняется по инструкции: `06-финальная-передача/Инструкция по верстке для Antigravity.md`.
- Один блок за один проход, сначала эталонный блок.
- Материалы вставляются из Google Drive по карте файлов.
- Проверяются переносы страниц, выравнивание, подписи, размеры кадров.

### 7. Валидация верстки

- Через BrowserSkill открывается итоговый документ.
- Проверяется каждая страница практической главы.
- Скриншоты проблемных мест сохраняются в `03-проверка/`.

### 8. Тест на неопытном читателе

- Документация даётся человеку, который никогда не играл в Тетрис.
- Задача: по документации начать играть без посторонней помощи.
- Фиксируются: места остановки, вопросы, непонятные шаги.
- Результаты вносятся в `03-проверка/Проверка на читателе.md`.

### 9. Финальная передача

- Документ в Google Docs содержит ссылку на Git-репозиторий.
- Репозиторий содержит рабочие записки, решения и результаты проверок.
- Финальный текст документации живёт в Google Docs, не в Git.

## Результаты обсуждения ошибок чтения

22.09.2026 с другом обсуждены ошибки, возникающие при чтении документации. Итоги обсуждения:

- подтверждена правильность пошагового стиля изложения;
- абстрактное объяснение должно идти раньше конкретного примера управления;
- примеры на картинках должны показывать результат действия, а не только нажатие;
- подписи к последовательности кадров должны описывать состояние, а не процесс.

Полный тест на неопытном читателе выполняется отдельно, его результаты будут зафиксированы после проведения.

## Правила фиксирования

- Каждая проверка фиксируется в `03-проверка/`.
- Каждое техническое действие фиксируется в `04-решения/Лог действий.md`.
- Важные решения фиксируются в `04-решения/История изменений.md`.
- Секреты и OAuth-данные в записки не заносятся.
